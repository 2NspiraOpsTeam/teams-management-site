## Quality and fidelity

Used the existing pinned **Sharp/libvips** locally; no image-generation API, paid editor, hosted upscaling service, new key or subscription. The process auto-orients, preserves aspect ratio, resamples with Lanczos3 and applies mild sharpening only to enlarged copies. It does not synthesize architecture, reconstruct signs, retouch property condition, change people/objects or replace a photograph. Logos use lossless WebP encoding. Original credits and licenses remain attached to their existing uses; these outputs are resized/re-encoded derivatives of those same sources.

115 sources received controlled upscaling; the remaining 153 retained native maximum dimensions. Saved covers are prepared up to four times their source dimensions within the chosen size policy. Small screenshots become larger, more consistently delivered images—not genuine newly recovered camera detail. For example, the selected Thai Super storefront starts at 539×534 pixels. A materially more detailed photograph still requires a better original; no substitute property photograph was introduced.

Public image surfaces now use responsive sizes, with small logo/thumbnail renditions rather than desktop files. Decorative covers can use prepared larger copies while retaining the existing native-cap layout logic. Gallery viewers have one current-photo full-size action; removed the duplicate Gold Street-only first-photo action. Cover selection, gallery order, property/unit associations, captions, alt text, crop/contain rules, motion, reduced-motion behavior and navigation were preserved.

Repeating grain textures retain their existing native CSS tile scale. External map/aerial tiles remain the provider's unmodified imagery; they are not property photographs and were not resampled or replaced.

## Delivery and publication integrity

- D1-linked generated bytes live in static assets, **not additional D1 image rows/blobs**. D1 media storage and the existing upload limits were not enlarged or weakened.
- Direct and encoded HTTP access to `_photo-variants` is blocked. Prepared photo requests must pass the **same existing `mediaResponse` publication SQL**, current visibility/property/unit checks and original source key/checksum comparison before bytes load.
- Only exact prepared widths and source hashes are accepted; no arbitrary image fetch, runtime resize or user-controlled processing.
- Versioned cache keys separate source, width, release and preview/publication scope, with the existing maximum 60-second revalidation window. Existing static originals retain their prior artifact/publication lifecycle.
- Lightweight prepared-photo handling runs before full Next rendering and shares the same browser security headers and request-error correlation wrapper. It never grants Admin/Tenant private access based on a public image request.
- New/unprepared sources retain existing original delivery. Changed/stale prepared sources fail closed rather than applying an old rendition to new bytes; re-inventory approved replacements.
- `build:preview:worker` stages checksum-verified renditions. Normal production builds do **not** stage them, and consumers outside preview scope keep their original source URLs. No production domain or DNS was changed.
