# Maintenance work-order MVP

## Audit and reuse
Existing tenant email OTP, role/session isolation, active apartment authorization, idempotent submissions, D1 request persistence and audit logging are retained. Existing admin maintenance APIs had no dedicated management screen, used non-atomic update/audit writes, and exposed only a current status. Tenant UI had no reference, detail route, attachments, timeline, entry consent or notifications.

No replacement framework/library/service is needed: reuse Next.js, D1, Gmail provider and existing design. No SMS, translation, dispatch, paid services, public launch or destructive migrations.

## Compatibility and migration
`work-orders-mvp.sql` adds companion detail, append-only event, private photo and channel-boundary outbox tables. Existing UUIDs and request rows remain unchanged. Numeric references are generated by SQLite AUTOINCREMENT. Legacy `in_review` and `scheduled` map to Under Review and In Progress without rebuilding the legacy CHECK constraint. Existing records receive submission and known current status facts only; missing historical transitions are explicitly labeled. Legacy staff notes stay private. All multi-record writes use D1 batch atomicity. Revision CHECK guards reject stale concurrent updates.

## Storage and limits
Photos are authenticated D1 records, never public media assets. JPEG/PNG/WebP only, signature checked, at most 650 KB each; four photos per submission, twelve total. This bounded $0 MVP reuses existing D1 rather than enabling paid object storage. Larger photos require resizing before upload; image conversion, malware scanning, retention policy and capacity review remain operational considerations before a broad production launch. Consider an already-approved private object store behind the same access route when volume warrants it; no store activated here.

## Notifications
Uses existing Gmail transport behind module outbox interface. Sender: WORK_ORDER_FROM or TENANT_AUTH_FROM. Management recipient: WORK_ORDER_NOTIFY_TO or existing INQUIRY_NOTIFY_TO. No recipient is invented. Notifications contain references, not tenant descriptions/photos/access instructions. Tenant email comes only from the authenticated email-OTP account. Submission atomically queues office/tenant notices; tenant updates queue office notice; status/tenant-visible management updates queue tenant notice. Internal-only notes send no mail. Failed/rejected notices remain visible for deliberate admin retry; ambiguous/sending outcomes never auto-resend. Provider acceptance is not inbox-delivery proof. No background scheduler or SMS introduced.

## Pending validation
Local lifecycle/security/failure tests, rendered responsive checks, migration preservation, candidate binding readiness and live inbox proof are tracked separately. Do not describe as production-ready before relevant gates pass.
